# یادداشت عملیات — هنوز مجوز انتشار عمومی نیست

## پیکربندی پایگاه

در توسعه، نبود `DATABASE_URL` به PGlite فایل‌محور می‌انجامد. در `NODE_ENV=production` نبود یا خالی‌بودن `DATABASE_URL` دیگر بی‌صدا پایگاه محلی نمی‌سازد: اتصال رد و `/api/health` وضعیت ۵۰۳ می‌دهد. برای پیش‌نمایش/آزمون محلیِ تک‌فرایندی فقط با `HERMICAD_ALLOW_PGLITE_IN_PRODUCTION=1` می‌توان این محافظ را صریحاً دور زد. این گزینه راهکار قابل اتکا برای چند replica، پشتیبان‌گیری، بازیابی یا انتشار عمومی نیست.

با `DATABASE_URL`، PostgreSQL استفاده می‌شود. در نخستین اتصال هر فرایند، `SCHEMA_DDL` افزایشی اجرا می‌شود؛ این سازوکار هنوز مهاجرت نسخه‌دار، قفل انتشار، طرح برگشت یا تضمین ایمنی ارتقای پایگاه واقعی نیست. شکست bootstrap اتصال را می‌بندد و بار بعد دوباره تلاش می‌کند. تنظیم اسرار و سیاست اتصال امن مسئول محیط است؛ نمونهٔ `.env.example` حاوی رمز واقعی نیست.

کنترل مبدأ درخواست‌های تغییردهنده بر **برابری میزبان** و **نشانهٔ خود مرورگر** تکیه می‌کند:

- `Origin` باید دقیقاً `scheme://host[:port]` باشد و میزبانش با میزبان درخواست یکی باشد. میزبان از `X-Forwarded-Host` (اگر proxy بفرستد) وگرنه از `Host` خوانده می‌شود. مبدأ ناشناخته، `null`، دارای مسیر یا دارای کاربر رد می‌شود.
- `Sec-Fetch-Site` اگر موجود باشد باید `same-origin` یا `none` باشد؛ این سرآیند را محتوای وب نمی‌تواند جعل کند.
- طرح‌واره فقط وقتی سخت‌گیرانه سنجیده می‌شود که proxy صریحاً `https` اعلام کند (`X-Forwarded-Proto`/`X-Forwarded-Ssl`).

**چرا طرح‌واره ملاک قطعی نیست:** خودِ Next.js روی هر درخواست `X-Forwarded-Proto` را بر اساس اتصالِ ورودی تنظیم می‌کند؛ پشت پراکسیِ TLS-خاتمه‌ده آن اتصال `http` است در حالی که مرورگر روی `https` کار می‌کند. اگر طرح‌واره شرط پذیرش باشد، همهٔ درخواست‌های نوشتن در چنین استقراری ۴۰۳ می‌شوند و برنامه عملاً از کار می‌افتد. برای همین، ملاک امنیتی «هم‌میزانی» و «نشانهٔ مرورگر» است و طرح‌واره فقط برای سخت‌گیری اضافی به کار می‌رود.

کوکی نشست روی https با `Secure` و `SameSite=None` صادر می‌شود تا داخل iframe و دامنهٔ میزبان کار کند؛ محافظت CSRF از بررسی مبدأ می‌آید، نه از `SameSite`. روی http ساده `SameSite=Lax` می‌ماند، چون مرورگر کوکیِ `None` بدون `Secure` را دور می‌ریزد.

پشت reverse proxy، proxy مورد اعتماد باید `Host`/`X-Forwarded-Host` را بر اساس اتصال بیرونی بازنویسی و مقادیر ارسالی کلاینت را حذف کند. سقف مصرف هر فضای کار با `HERMICAD_QUOTA_PROJECTS` (پیش‌فرض ۲۰۰) و `HERMICAD_QUOTA_DESIGNS` (پیش‌فرض ۳۰۰) قابل تنظیم است و از پر شدن پایگاه توسط یک بازدیدکننده جلوگیری می‌کند.

`GET /api/health` تنها اتصال پایگاه و `SELECT 1` را می‌سنجد، `no-store` است و جزئیات زیرساخت را افشا نمی‌کند. پاسخ موفق این مسیر نه صحت داده و مهاجرت، نه سلامت کامل سامانه، نه مجوز انتشار را اثبات می‌کند. پایش عملیاتی، هشدار، محدودیت نرخ و اهداف دسترس‌پذیری هنوز باید طراحی و آزموده شوند.

## بستهٔ استقرار (Docker)

```bash
docker compose up -d --build          # Postgres + برنامه، هر دو با سلامت‌سنجی
HERMICAD_PORT=8080 docker compose up -d --build
docker compose --profile preview up -d --build hermicad-preview   # فقط پیش‌نمایش بدون Postgres
```

قرارداد تصویر در `Dockerfile`:

- چندمرحله‌ای است؛ تصویر نهایی فقط وابستگی‌های production را دارد (`npm ci --omit=dev`).
- عمداً از `output: "standalone"` استفاده نشده: آن حالت با `next start` — همان دستوری که `test:http`، `test:smoke` و CI اجرا می‌کنند — ناسازگار است. تصویر همان مسیری را اجرا می‌کند که آزمون‌ها می‌سنجند، پس «در تصویر کار می‌کرد» و «آزمون می‌شد» دو چیز جدا نیستند.
- با کاربر `node` (غیر ریشه) و `tini` به‌عنوان PID 1 اجرا می‌شود؛ `SIGTERM` به Node می‌رسد و خاموشی تمیز انجام می‌شود.
- `HEALTHCHECK` روی `/api/health` است. پایش بیرونی هم لازم است: این سنجه فقط اتصال پایگاه را می‌آزماید.
- در compose، سرویس برنامه با فایل‌سیستم فقط‌خواندنی، `cap_drop: ALL` و `no-new-privileges` اجرا می‌شود؛ پایگاه پورت عمومی ندارد و فقط در شبکهٔ داخلی است.
- `.dockerignore` فایل‌های `.env*` را بیرون نگه می‌دارد تا هیچ سرّی در لایه‌های تصویر نماند.

`.github/workflows/quality.yml` سه کار دارد: دروازهٔ کیفیت، آزمون یکپارچگی Postgres، و
`smoke` که خروجی build را با `next start` بالا می‌آورد و جریان کامل کاربر را می‌سنجد.

## نگهداشت داده و کش

| متغیر | پیش‌فرض | معنا |
| --- | --- | --- |
| `HERMICAD_RUN_RETENTION` | ۲۰ | حداکثر اجراهای نگه‌داشته‌شدهٔ هر پروژه |
| `HERMICAD_QUALITY_TTL_MS` | ۱۵۰۰۰ | مدت اعتبار کش نتیجهٔ دروازهٔ کیفیت |
| `HERMICAD_PUBLIC_URL` | — | دامنهٔ عمومی برای `robots.txt` و `sitemap.xml` |

**نگهداشت اجراها.** اندازه‌گیری روی نمونهٔ واقعی نشان داد هر تولید پنج‌طرحی حدود
۱٫۱ مگابایت (طرح، گزارش، تصویر نسخه) به پایگاه اضافه می‌کند. بدون سقف، یک حساب
می‌توانست با تولید مکرر پایگاه یک سامانهٔ عمومی و رایگان را پر کند. اکنون پس از هر
تولید، اجراهای مازاد در همان تراکنش حذف می‌شوند (آبشار پایگاه داده). دو استثنا:

- **اجرای فعال** پروژه هرگز حذف نمی‌شود؛ حذفش یعنی از دست رفتن طرحی که کاربر می‌بیند.
- **اجراهای پیش از مهاجرت** (بدون اثر انگشت مجموعه قواعد) هرگز حذف نمی‌شوند: منشأ
  کامل ندارند، بازتولیدشدنی نیستند و تنها نسخهٔ آن تاریخ‌اند. تضمین «تولید مجدد دادهٔ
  قدیمی را حذف نمی‌کند» همچنان برجاست.

هر دو رفتار آزمون دارند: `scripts/qa-retention-http.ts` (سقف و اجرای فعال) و
`scripts/qa-legacy-http.ts` (بقای رکورد قدیمی پس از تولید مجدد). اگر سقف را کم کنید،
تاریخچهٔ مقایسهٔ پروژه کوتاه می‌شود؛ اگر صفر یا نامعتبر بدهید، حداقل ۱ اعمال می‌شود و
هیچ‌گاه «بی‌سقف» نمی‌شود.

**کش دروازهٔ کیفیت.** `/quality` و `/api/quality` نتیجهٔ اجرای سوئیت را برای
`HERMICAD_QUALITY_TTL_MS` نگه می‌دارند؛ بدون آن هر بازدید حدود ۴ ثانیه CPU می‌گرفت و
یک دیدار عمومی ساده می‌توانست سرور را اشغال کند. `/` از خلاصهٔ ایستا استفاده می‌کند.
این کش فقط نمایشی است و بر خروجی مهندسی هیچ مسیری اثر ندارد.

**کش HTTP.** `proxy` به‌طور پیش‌فرض `no-store` می‌گذارد چون پاسخ‌ها به کوکی فضای کار
وابسته‌اند. تنها `/api/catalog` عمومی است و `public, max-age=3600` می‌گیرد؛ این استثنا
فهرست صریح است، نه حدس از روی پاسخ (در لایهٔ middleware پاسخ مسیر هنوز ساخته نشده).

## دامنهٔ عمومی، robots و sitemap

`/robots.txt` فقط مسیرهای عمومی را مجاز می‌کند و `/api/`، `/share` و همهٔ زیرمسیرهای
مخصوص یک فضای کار (`/projects/*`، `/design/*`) را می‌بندد؛ محتوای یک فضای کار نباید
در موتور جست‌وجو ایندکس شود. `/sitemap.xml` هشت مسیر عمومی را با نشانی مطلق می‌آورد.

هر دو در زمان درخواست ساخته می‌شوند: نشانی پایه از `HERMICAD_PUBLIC_URL` خوانده می‌شود و
اگر تنظیم نشده باشد از `X-Forwarded-Host`/`Host` درخواست. این انتخاب عمدی است — نسخهٔ
ایستا در زمان build متغیر محیطی را نداشت و sitemap خالی منتشر می‌شد. در استقرار پشت
پراکسی، تنظیم صریح `HERMICAD_PUBLIC_URL` توصیه می‌شود تا نشانی‌ها به میزبان درخواست
کاربر وابسته نباشند.

## اجرای آزمون‌ها

```bash
npm ci
npm run lint
npm run typecheck
npm test
npm run build
npm run test:http
npm run test:smoke     # نیاز به سرور در حال اجرا؛ BASE=http://127.0.0.1:3000
npm audit --omit=dev --audit-level=high
```

`test:http` سرور production موقت، fixture دادهٔ قدیمی و پایگاه PGlite دورریختنی می‌سازد. همچنین حالت production بدون تنظیم پایگاه را در فرایند جدا و پوشهٔ موقت بررسی می‌کند. برای PostgreSQL، صرفاً از پایگاه **اختصاصی آزمایش و دورریختنی** استفاده کنید و `HERMICAD_QA_POSTGRES_URL` و `HERMICAD_QA_ALLOW_POSTGRES=1` را تنظیم کنید؛ اسکریپت schema تصادفی می‌سازد و در پایان حذف می‌کند. دسترسی به پایگاه تولید به این آزمون ندهید. آزمون مرورگر اختیاری به Playwright و Chromium سازگار با میزبان نیاز دارد.

## موارد مسدودکنندهٔ استقرار واقعی

- محیط و دامنهٔ واقعی، HTTPS، مدیریت و چرخش اسرار، تفکیک دسترسی، سیاست شبکه و ثبت رخداد عملیاتی تصویب و پیاده‌سازی نشده‌اند.
- نسخه‌بندی مهاجرت، ارتقا و rollback، پشتیبان رمزگذاری‌شده در محل جدا و **آزمون واقعی بازیابی** داده و فایل‌ها وجود ندارد. سقف نگهداشت اجراها (بالا) فقط رشد را محدود می‌کند؛ جای پشتیبان و سیاست نگهداری مصوب را نمی‌گیرد. آزمون تکرار bootstrap با fixture مصنوعی جایگزین آن‌ها نیست.
- صف، سهمیه و کنترل بار سراسری، اجرای چند replica، حد زمان/منابع، برنامهٔ پاسخ به حادثه، تست نفوذ مستقل و اهداف RTO/RPO و بار تأیید نشده‌اند. آزمون داخلی ظرفیت قاب به معنی آزمون بار چندکاربره نیست.
- تاریخچهٔ پروژه‌ها تغییرناپذیر نیست، فایل artifact در سیستم ذخیره نمی‌شود و با حذف پروژه داده‌های وابسته حذف می‌شوند. سیاست داده، محرمانگی، مجوزها، پشتیبانی و تأمین هزینه هنوز تصمیم مصوب ندارند.
- آمادگی نرم‌افزاری، اعتبار مهندسی و بهره‌برداری عمومی سه دروازهٔ جدا هستند؛ موفقیت اتصال یا CI محلی هیچ‌یک را به‌تنهایی نمی‌بندد.
